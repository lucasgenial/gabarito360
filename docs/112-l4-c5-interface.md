# 112 — L4-C5: interface e ensaio integrado

Planejamento revisto antes de implementar. Autorização de continuidade do usuário abrange todas as divisões internas de L4; executar Git/testes sem pedir aprovação de cada divisão. Publicar somente ao fechar L4 (nível1). Inventário consultado: não existe tela específica de exportação; origem é aprovação explícita e contratos107–111. Reutilizar layout/tokens/formulários de pedidos106.

Interface: responsável interno vincula aluno por referência validada e evidência; administrador/proprietário consulta protocolo conhecido por UUID e confirma aluno, campos, destinatário e prazo antes de conceder. Não criar busca global de pessoas. Tela de exportações aceita referência de concessão para gerar e referência de artefato para consultar/baixar; recibos exibem referências copiáveis e links de continuidade. Revogação exige versão e motivo e permanece disponível sem conferências vigentes. Cada rota revalida papel/contexto; a API continua autoridade. Concluir protocolo permanece separado de exportar.

Mutações usam tickets cifrados vinculados a sessão/contexto, UUID idempotente e confirmação explícita. Repetição de falha usa payload original e nunca novo UUID. Não guardar nomes/evidências em flash, logs ou HTML de erros. Prazo informado em Brasília convertido a UTC. Download web faz proxy autenticado pela API e só retorna bytes após sucesso, como anexo opaco sem cache; token nunca chega ao navegador. Flag de interface de exportação desligada. Testar autorização, contexto, falhas, repetição e escape; conferir apresentação no Chrome local com dados fictícios. Ensaiar concorrência em MariaDB isolado. Nenhum teste de dados reais ou deploy nesta parte.
